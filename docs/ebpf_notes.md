# Day 27: eBPF 最小必要概念
## 1. eBPF 是什么？ (extended Berkeley Packet Filter)
**核心定义：** eBPF 是一种革命性的内核技术，它允许开发者在不修改内核源代码、也不需要重新编译或加载传统内核模块（Kernel Module）的情况下，在 Linux 内核内部安全地运行沙盒程序（Sandboxed Programs）。

**技术本质：**

+ **起源与演进：** 最早的 BPF 是为了高效过滤网络数据包（如 `tcpdump` 的底层机制）而设计的。加上 "extended" 后，它演变成了一个通用的内核态虚拟机。
+ **事件驱动（Event-Driven）：** eBPF 程序是事件驱动的。当内核或用户态程序执行到特定的钩子（Hooks）时，就会触发 eBPF 程序的执行。这些钩子包括系统调用（Syscalls）、函数进入/退出（kprobes/uprobes）、网络事件、跟踪点（Tracepoints）等。
+ **安全性（Verifier）：** 任何 eBPF 代码在注入内核之前，都必须经过极其严格的**验证器（Verifier）**检查。验证器确保代码不会导致内核崩溃（Panic）、没有死循环，且不会越权访问未授权的内存。
+ **高性能（JIT）：** eBPF 字节码会被即时编译（JIT, Just-In-Time）成本地机器码，以接近原生的速度在内核中执行。

## 2. BCC 是什么？ (BPF Compiler Collection)
**核心定义：** BCC 是一个开源的工具包和库集合，专门用于简化 eBPF 程序的编写、编译和加载过程。

**存在的意义与解决的痛点：**

+ **降低门槛：** 原生的 eBPF 编程需要编写 C 代码，通过 LLVM 编译成 eBPF 字节码，再手动通过 `bpf()` 系统调用加载，操作极其繁琐。
+ **前后端分离架构：** BCC 允许你使用 **C 语言** 编写内核态的 eBPF 核心逻辑（数据采集），并使用高级语言（如 **Python** 或 **Lua**）编写用户态的前端脚本。前端脚本负责把 C 代码编译注入内核，并读取、处理、展示采集到的数据。
+ **开箱即用的工具箱：** BCC 官方仓库中自带了数十个极为强大的现成性能分析工具（如 `execsnoop`, `opensnoop`, `biolatency`），覆盖了 CPU、内存、网络、磁盘 I/O 等全方位的观测场景。

## 3. 为什么 eBPF 极其适合做“动态观测”？
传统的观测手段（如修改业务代码打日志、使用外部 agent 轮询）往往具有侵入性强、性能损耗大、视角受限等缺点。eBPF 在动态观测上具备以下压倒性优势：

+ **零侵入性（Non-intrusive）：** 不需要重启服务，不需要修改业务代码，也不需要重新编译内核。探针（Probes）可以随时动态挂载和卸载，对正在运行的生产环境极其友好。
+ **极低的性能开销（Low Overhead）：** 传统方案在抓取底层数据时，经常需要将大量数据从内核态拷贝到用户态，引发昂贵的上下文切换。eBPF 允许在**内核态直接聚合和过滤数据**（通过 BPF Maps 结构，如哈希表、直方图），只把最终的统计结果发送给用户态，极大地节省了 CPU 和总线带宽。
+ **上帝视角的可见性（Full-stack Visibility）：** eBPF 打破了应用与内核之间的黑盒边界。它不仅能观测用户态程序的函数调用（uprobes），还能深入观测内核的网络协议栈、文件系统、进程调度（kprobes），实现端到端、全链路的性能剖析。
+ **绝对的安全性（Safety）：** 相比于传统开发内核模块（一旦写出 Bug 就会导致整个操作系统 Kernel Panic 蓝屏/死机），eBPF 验证器从根本上杜绝了这种风险，这使得大厂敢于在核心生产服务器上大规模部署 eBPF 监控。
