## **1. 实验目标与背景**

**验证在** **HTTP 短连接** **场景下，操作系统 TCP 状态机的演变规律。通过自主编写的异步压测客户端** `**short_conn_client.py**` **向 Nginx 靶机发起高频请求，复现并观测** `**TIME_WAIT**` **堆积现象，从而理解四次挥手中“主动关闭方”的资源代价。**

## **2. 观测数据 (Observed Metrics)**

**在压测峰值期间，通过系统底层工具捕获到以下核心指标：**

```latex
# 观测命令: ss -s
TCP: 8453 (estab 86, closed 8263, orphaned 31, timewait 8187)

# 观测命令: ss -ant | grep TIME-WAIT | wc -l
Output: 8188
```

**关键发现：** 压测开始后 10 秒内，TIME_WAIT 状态连接数从个位数激增至 **8000+**，且系统软中断 (si) CPU 占用显著上升，说明内核正在高频处理 TCP 分节的回收逻辑。

## 3. 根因分析 (Root Cause Analysis)

本次 `TIME_WAIT` 激增的产生遵循 TCP 协议设计的标准行为：

- **主动关闭身份确认：** 客户端脚本显式设置了 `Connection: close` 请求头，并配置了 `force_close=True`。这使得每次 HTTP 请求完成后，**客户端** 率先发送 `FIN` 分节，成为 TCP 四次挥手里的“主动关闭方”。
- **2MSL 等待机制：** 根据 RFC 793，主动关闭方在发送最后一个 `ACK` 后必须进入 `TIME_WAIT` 状态，等待 2 个 MSL（Linux 默认为 60s）以确保对端收到 ACK 并让旧分节在网络中自然消失。
- **资源错配：** 压测速率约为 2000 QPS，而回收周期固定为 60s。这种“快进慢出”的模式导致本地临时端口（Ephemeral Ports）被迅速占满。

## 4. 实验过程中的“盲区”复盘

**观测失误记录：** 在实验初期，快照脚本 `snapshot.sh` 错误使用了 `ss -ntlp` 命令。

**分析：**`-l` 参数仅过滤 `LISTEN` 状态的 Socket，导致在压测最猛烈时，观测结果依然显示“网络正常”。这警示我们在 SRE 排障中，工具参数的细微差别可能导致彻底误判现状。

## 5. 生产环境防御建议 (Remediation)

针对高频短连接引发的端口耗尽风险，生产环境应采取以下工业级标准配置：

| **维度**   | **解决方案**                | **原理**                                          |
| ---------- | --------------------------- | ------------------------------------------------- |
| **应用层** | 长连接/连接池 (Keep-Alive)  | 消除频繁的三次握手与四次挥手，降低内核损耗。      |
| **内核层** | `net.ipv4.tcp_tw_reuse = 1` | 允许系统在安全的情况下复用 TIME_WAIT 状态的端口。 |
| **架构层** | 四层负载均衡 (L4 LB)        | 通过多 IP 绑定分散压力，扩大可用端口池空间。      |
